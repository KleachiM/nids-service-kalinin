### 2.4. Намеренный конфликт слияния

От одного состояния `main` (`e65c424`) созданы две ветки:

```bash
git branch exp/alpha
git branch exp/beta
git switch exp/alpha
```

В обеих ветках изменена одна строка описания сервиса. В `exp/alpha` добавлено
упоминание модели машинного обучения (`2c0eb43`), в `exp/beta` — HTTP API
(`c9ed430`). Оба изменения закоммичены, ветки отправлены на сервер:

```bash
git push origin exp/alpha exp/beta
git switch main
git merge --no-ff exp/alpha -m "Слить ветку exp/alpha в main"
git merge --no-ff exp/beta -m "Слить ветку exp/beta в main"
```

Слияние `exp/alpha` завершилось merge-коммитом `4df3078`. При слиянии
`exp/beta` получен конфликт:

```text
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

Конфликтный блок из README, дополнительно восстановленный при подготовке
отчёта из общего предка и двух реальных версий файла:

```text
<<<<<<< HEAD
Сервис детектирования аномалий сетевого трафика с помощью модели машинного обучения. Учебный сквозной проект
=======
Сервис детектирования аномалий сетевого трафика с HTTP API. Учебный сквозной проект
>>>>>>> exp/beta
```

- `<<<<<<< HEAD` начинает вариант текущей ветки `main`, уже содержащей изменения `exp/alpha`.
- `=======` разделяет два конфликтующих варианта.
- `>>>>>>> exp/beta` завершает вариант вливаемой ветки `exp/beta`.

Git не может самостоятельно определить, какое уточнение нужно оставить.
Конфликт разрешён вручную: сохранён смысл обоих изменений, маркеры удалены.

```text
Сервис детектирования аномалий сетевого трафика с помощью модели машинного обучения и HTTP API. Учебный сквозной проект
```

Слияние завершено и отправлено в `main`:

```bash
git add README.md
git commit -m "Разрешить конфликт описания сервиса при слиянии exp/beta"
git push origin main
```

Получен merge-коммит `b5d6c21` с двумя родителями. Учебные ветки удалены:

```console
$ git push origin --delete exp/alpha exp/beta
 - [deleted]         exp/alpha
 - [deleted]         exp/beta
$ git branch -d exp/alpha exp/beta
Deleted branch exp/alpha (was 2c0eb43).
Deleted branch exp/beta (was c9ed430).
```

Удаление веток убирает указатели, но не удаляет коммиты, вошедшие в `main`.

### 2.6. Уже закоммиченный файл и `.gitignore`

Проверка пункта 20 выполнена в отдельной временной копии, чтобы не добавлять
двоичную модель в опубликованную историю проекта. Сначала модель добавлена
и закоммичена, затем отдельным коммитом добавлено правило `*.pkl`:

```bash
git add model.pkl
git commit --quiet -m "Добавить учебную модель в проверочной копии"
# В .gitignore добавлена строка *.pkl.
git add .gitignore
git commit --quiet -m "Добавить правило игнорирования в проверочной копии"
```

После этого файл всё ещё находится в индексе. После изменения его содержимого
Git продолжает показывать его в статусе:

```console
$ git ls-files -- model.pkl
model.pkl
$ git status --short
 M model.pkl
```

Причина: `.gitignore` действует на неотслеживаемые файлы и не исключает
автоматически файлы, уже включённые в индекс. Чтобы перестать отслеживать
файл, сохранив его на диске, выполнено:

```console
$ git rm --cached model.pkl
rm 'model.pkl'
$ git status --short
D  model.pkl
$ git check-ignore -v model.pkl
.gitignore:26:*.pkl	model.pkl
$ git commit --quiet -m "Убрать модель из индекса в проверочной копии"
$ git status --short
```

Проверено, что `model.pkl` остался на диске, а рабочее дерево стало чистым.
Статус `D ` перед коммитом обозначает подготовленное удаление из следующего
снимка Git. Старые коммиты по-прежнему содержат модель. Если таким образом
случайно опубликован настоящий пароль, одного игнорирования недостаточно:
пароль необходимо заменить, поскольку он уже раскрыт в истории.

### 2.7. Отмена опубликованного изменения

В `main` намеренно удалены 45 строк README: разделы о структуре, тестах,
качестве модели и переменных окружения. Создан и отправлен плохой коммит:

```console
$ git commit -m "Удалить половину README для демонстрации отмены коммита"
[main 7f8904b] Удалить половину README для демонстрации отмены коммита
 1 file changed, 45 deletions(-)
$ git push origin main
   b196844..7f8904b  main -> main
```

Отмена выполнена через `git revert --no-commit`, чтобы затем задать понятное
сообщение коммита на русском языке:

```console
$ git revert --no-commit 7f8904b
$ git commit -m "Восстановить README отменой учебного коммита"
[main 4a6d22b] Восстановить README отменой учебного коммита
 1 file changed, 45 insertions(+)
$ git push origin main
   7f8904b..4a6d22b  main -> main
$ git diff --exit-code 7f8904b^ 4a6d22b
```

Последняя команда завершилась с кодом 0 без вывода: все отслеживаемые файлы
совпали с состоянием до плохого коммита.

`revert` создаёт новое изменение, обратное выбранному коммиту. Плохой коммит
и его отмена остаются в общей истории. `reset --hard` перемещает указатель
текущей ветки и заменяет индекс и отслеживаемые файлы рабочего каталога;
незакоммиченные изменения могут быть потеряны. Для публикации такого отката
обычно понадобился бы принудительный push, создающий расхождение с копиями
коллег. Поэтому для отмены этого опубликованного коммита использован `revert`.

## 3. Ответы на контрольные вопросы

### 1. Чем коммит отличается от сохранённой версии файла? Что он хранит?

Коммит фиксирует состояние всего проекта, подготовленное в индексе, а не
только одну версию одного файла. Объект коммита ссылается на дерево файлов
и родительские коммиты, содержит автора, коммитера, время и сообщение.
Дерево ссылается на содержимое файлов. Разницу между версиями Git вычисляет
сравнением снимков; неизменённые объекты можно использовать повторно.

### 2. Для чего нужен индекс?

Индекс позволяет отдельно выбрать содержимое следующего коммита. Например,
я могу добавить исправление README, оставив незавершённое изменение кода
в рабочем каталоге. Можно включить даже отдельные фрагменты одного файла
через `git add -p`, разделив независимые изменения на понятные коммиты.

### 3. Почему ветка создаётся мгновенно?

Создание ветки добавляет ссылку на существующий коммит. Git не копирует
каталог проекта и историю файлов. Поэтому стоимость создания указателя
практически не зависит от размера проекта. Переключение ветки при этом
может потребовать обновления файлов рабочего каталога.

### 4. Что попадёт в коммит после `git add`, нового изменения и `git commit`?

В коммит попадёт версия, которая была помещена в индекс командой `git add`.
Последующее изменение останется только в рабочем каталоге, пока я снова
не выполню `git add`. Обычный `git commit` берёт содержимое из индекса.

### 5. Почему датасет на 3 ГБ не следует хранить в обычном Git?

Большой датасет увеличивает объём объектов и стоимость хранения истории.
Его загрузка и клонирование требуют много времени, трафика и места на диске
у каждого участника и в CI. Частые изменения двоичных или сжатых данных могут
плохо сжиматься и давать мало полезных различий для ревью; ограничения хостинга
могут вообще не позволить отправить такой файл. Удаление файла новым коммитом
не уберёт старые версии из истории. Для данных и моделей подходят внешнее
хранилище с DVC либо Git LFS с учётом ограничений выбранного сервиса.

### 6. Что означают конфликтные маркеры?

При обычном слиянии `<<<<<<< HEAD` открывает вариант текущей ветки,
`=======` отделяет его от варианта вливаемой ветки, а `>>>>>>> имя-ветки`
закрывает второй вариант. Нужно выбрать или объединить содержимое, удалить
маркеры, проверить результат и добавить файл в индекс для завершения слияния.

### 7. Чем отличаются `revert` и `reset`? Когда `reset` мешает коллегам?

`revert` сохраняет историю и добавляет новый коммит с обратным изменением.
`reset` передвигает текущую ветку к выбранному состоянию; режимы определяют,
будут ли также изменены индекс и рабочий каталог. Если передвинуть уже
опубликованную ветку назад и принудительно отправить её, у коллег останутся
коммиты старой истории. Им придётся вручную согласовывать свои ветки с новой
историей, и чужая работа может быть затёрта. В общей опубликованной ветке
для обычной отмены изменения безопаснее использовать `revert`.

## 4. Возникшие затруднения и способы их устранения

1. **Неправильные параметры `git log`.** Команды `git log --one-line` и
   `git log -oneline` завершились ошибкой `fatal: unrecognized argument`.
   Правильная запись — `git log --oneline`: два дефиса и слитное имя параметра.
2. **Локальная `main` отставала от GitHub.** Перед созданием конфликтующих веток
   обнаружены три отсутствующих локально коммита, включая слияние PR №1.
   Выполнены `git fetch origin` и `git merge --ff-only origin/main`, после чего
   обе учебные ветки созданы от одной актуальной базы.
3. **Конфликт одной строки README.** Две ветки содержали полезные уточнения.
   Вместо удаления одного из них текст объединён вручную, маркеры удалены,
   слияние завершено отдельным коммитом. Дополнительно проверено отсутствие
   конфликтных маркеров в README.
4. **Шаблон уже содержал `AUTHOR.md`.** При повторной проверке получен статус
   ` M`, а не `??`. Проверка исходного коммита показала, что файл уже
   отслеживался. В отчёте приведён фактический переход ` M` → `M ` и отдельно
   объяснён случай нового файла.
5. **`.gitignore` не скрывал отслеживаемую модель в проверочной копии.**
   Правило игнорирования не удаляет файл из индекса. Помогли
   `git rm --cached model.pkl` и коммит удаления; локальный файл сохранился.

Проверки касались Git и документации. Тесты HTTP-сервиса и повторное обучение
модели при выполнении этой лабораторной работы не запускались; метрики из
шаблона README не выдаются за результаты нового эксперимента.
